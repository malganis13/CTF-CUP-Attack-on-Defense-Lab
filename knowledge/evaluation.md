# Честная оценка: тянет ли он роль четвёртого игрока

Короткий ответ: **нет, не игрока.** Он тянет роль санитара команды — того, кто
снимает рутину и не даёт забыть про дыру. Разница принципиальная, и её лучше
знать до игры, а не на игре.

## Что он делает лучше человека

| Задача | Человек | Инструмент |
|---|---|---|
| Карта сервисов | 5–15 минут, зависит от усталости | один прогон, все порты, pid, cwd, стек |
| Поиск опасных мест в 19 файлах | час на первый проход | секунды, 55 правил, 10 языков |
| «А где это было?» | поиск по памяти | файл:строка, контекст ±3 строки |
| Отчёт команде | пишется в конце, когда сил нет | markdown по кнопке |
| Первая проба на дыру | 10–20 минут на написание | 4 запроса, таблица улик |
| Повторяемость | зависит от того, кто дежурит | одинаково в 10:00 и в 17:50 |

## Что он делает хуже человека

| Задача | Почему |
|---|---|
| Понять бизнес-логику | «перевод между счетами без проверки баланса» не ловится регуляркой |
| Построить цепочку | «IDOR → админ → SSRF → файл с флагами» — это рассуждение, не паттерн |
| Придумать новую дыру | правила ищут известные формы; новая форма — вне их |
| Отличить дыру от мусора | эвристика даёт кандидатов, ложные срабатывания неизбежны |
| Прочитать бинарник | только исходники и манифесты |
| Понять протокол чекера | намеренно не касается `/_checker/*` |
| Решить, что патчить первым | приоритет по важности — не приоритет по очкам |

## Где он врёт (и как это видно)

- **Ложное срабатывание.** Правило `path-join` ловит `os.path.join(root, name)`,
  даже если `name` уже проверен выше. Лечится чтением контекста, а не доверием.
- **Пропуск.** Данные текут через три функции — правило на строке ничего не
  увидит. Пропуск опаснее ложного срабатывания: его не видно.
- **Маркер не тот.** Проба ищет `sqlite3.` в ответе; сервис на PostgreSQL
  ответит иначе. Тогда будет `чисто` при живой дыре.
- **Один параметр.** Проба бьёт в первый найденный параметр. Если дыра во
  втором — промах.

Всё это написано в интерфейсе: «эвристики, не доказательства».

## Числа из проверок

- `tools/test_probe.py` — **38/38**: пять классов находятся на живом HTTP,
  на чистой ручке ни один не срабатывает, чекер не запрашивается, бюджет
  держит, экспортированный скрипт работает отдельным процессом.
- `tools/smoke.py` — **65/65**: все ручки API, языки, стеки, генератор,
  запуск пробы через сервер, отчёт, линтер.
- Демо-набор: 19 файлов, 10 языков, 12 сервисов, 52 находки.

Чего эти числа **не** доказывают: что на чужом фреймворке с другими ответами
маркеры совпадут. Лаборатория написана под свои же маркеры — это проверка
механики, а не качества эвристик на незнакомом коде.

## Как его правильно ставить в команду

1. **До игры.** Прогнать на тренировочном vulnbox, руками проверить, что
   находки не мусорные, поправить маркеры под свои сервисы.
2. **Первый час.** Аудит своей коробки → список дыр → патчи по одной. Это
   защита, она стоит больше атаки.
3. **Середина игры.** Проба по одной-двум находкам у соседей, с бюджетом,
   без перебора.
4. **Последний час.** Отчёт и список непочиненных — чтобы не забыть.

Он не заменяет игрока. Он не даёт трём игрокам забыть, что они втроём.

## Что бы дало больше всего на следующем шаге

- Проверка патча: после правки прогнать ту же пробу и увидеть `чисто` — это
  уже есть, но руками.
- Сверка «находка → правка → повторная проба» в один отчёт.
- Больше маркеров под конкретные стеки (Postgres, MySQL, Java stack traces).
