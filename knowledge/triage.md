# Триаж находок

Правило первое: находка — это место, которое надо прочитать, а не баг.

## Порядок

1. **`checker risk: high`** — сначала это. Если в файле есть `/_checker` или
   `putflag`/`getflag`, читаем как документацию: где чекер хранит флаг, каким
   API его отдают. Атаковать этот путь нельзя, но он показывает, где флаг
   лежит.
2. **SQL-инъекция с конкатенацией** — самый частый реальный вектор в A/D.
   Проверяется одним GET-запросом, чинится за десять минут.
3. **IDOR / BOLA** — второй по частоте. Объект берётся по `id` без владельца.
   Проверка: два соседних id, оба отдаются.
4. **Path traversal** — читает файлы, часто включая конфиг с флагом или
   sqlite-базу.
5. **Deserialization / SSTI / command injection** — реже, но сразу RCE.
6. **Mass assignment** — `role` из тела запроса. Даёт админа без пароля.
7. **JWT bypass** — `verify=False` или `alg: none`.
8. **Hardcoded secret / debug** — не флаг, но открывает дверь.

## Быстрый признак настоящей дыры

Данные из запроса доходят до опасного вызова **без преобразования**. Если
между ними есть `int()`, allowlist, параметризованный запрос — это не дыра, а
шум. Смотреть контекст ±3 строки, а не строку.

## Что делать после триажа

- Дыра у себя → патч (см. `patch-playbook.md`).
- Дыра у соседа → проба (см. `attack-playbook.md`), но только после того, как
  свой сервис стабилен.
