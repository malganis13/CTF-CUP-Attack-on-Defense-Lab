# Вулнбокс турнира: как он устроен и что с паролями

Короткий ответ на три вопроса, которые возникают в первые минуты: где живёт
цель, какие на ней учётки и что менять, чтобы не сломать чекер.

## Один хост, много сервисов

В Attack–Defense команде выдаётся **одна машина** — вулнбокс. На ней поднято
несколько сервисов, каждый слушает свой порт. Чекер ходит в сервис по адресу
`http://<ip вулнбокса>:<порт>/...` и проверяет функциональность. Отсюда модель:

- **хост** — один, его адрес и есть адрес команды;
- **сервис** — процесс, контейнер или юнит systemd на своём порту;
- **пользователь** — SSH-доступ обычно один (`root`), внутренние учётки сервисов
  (БД, админка) живут внутри приложения.

«Один сервис — один хост» в CUP не бывает. Бывает `10.10.X.Y:8081`,
`10.10.X.Y:8082`, `10.10.X.Y:8083` — три сервиса на одной машине. Именно так
устроен и локальный полигон: `127.0.0.1:2222` — SSH, `:8081` — notes,
`:8082` — archive, `:8083` — warehouse.

Порты и юниты видно кнопкой **«опросить цель»** на вкладке «Стенд»: инструмент
читает `ss -lntp`, `systemctl`, каталоги `/srv`, `/opt`, `/home` и `docker ps`
одним SSH-заходом. Снаружи он ничего не сканирует.

## Какие учётки бывают

| Учётка | Где используется | Менять? |
|---|---|---|
| SSH `root` | вход на вулнбокс | да, если выдан пароль; ключ оставить |
| SSH служебный (`vulnbox`, `svc`) | вход без root | да, если он есть |
| пользователь БД | приложение → БД | только вместе с конфигом приложения |
| админ панели сервиса | веб-интерфейс | по ситуации, чекер обычно не ходит |

Правило простое: **меняйте то, чем входят снаружи**. Пароль БД, прописанный в
`config.py` сервиса, менять можно только одновременно с конфигом и
перезапуском — иначе сервис ляжет и чекер начнёт отдавать нули.

## Когда менять пароли

1. **В начале первого раунда** — до того, как соседи успели прочитать выданные
   учётки. Это дешёвая защита: старый пароль перестаёт работать сразу.
2. **После утечки** — если пароль был в конфиге, в логах, в отданном файле.
3. **После подозрительного входа** — но сначала выясните, через что вошли:
   смена пароля не закрывает дыру в сервисе.

Не меняйте пароль во время раунда, если чекер ходит этим аккаунтом: вы
перезапустите проверку на середине. В локальном полигоне чекер лежит в
`/srv/_checker/checker.py`, его можно прогнать вручную: `python3
/srv/_checker/checker.py --once`. В турнире — дождитесь результата раунда.

## Как менять: три способа

**1. Через инструмент.** Вкладка «Подключение» → блок «Смена пароля на цели».
Пользователь, пустой пароль — сгенерирую 20 символов. Пароль уходит в
`chpasswd` через stdin, не в командную строку, и не пишется на диск. После
смены инструмент проверяет вход новым паролем отдельным соединением.

**2. Руками по SSH.**

```bash
# интерактивно, без эха в истории
passwd root

# неинтерактивно: пароль в stdin, не в аргументах
printf 'root:%s\n' "$NEW" | chpasswd
```

**3. Ключом вместо пароля.** Надёжнее и не мешает чекеру:

```bash
install -d -m 700 /root/.ssh
cat >> /root/.ssh/authorized_keys <<'KEY'
ssh-ed25519 AAAA... your-key
KEY
chmod 600 /root/.ssh/authorized_keys
```

Ключ добавляйте **до** того, как отключать пароль, и проверяйте вход вторым
терминалом. Иначе можно закрыть себе доступ.

## sshd: почему root не пускает по паролю

На Debian/Kali по умолчанию `PermitRootLogin prohibit-password`: root входит
только ключом. Если в турнире выдан пароль root и нужен именно он:

```bash
printf '%s\n' 'PermitRootLogin yes' > /etc/ssh/sshd_config.d/99-ad.conf
sshd -t && systemctl reload ssh
```

Проверка политики — в ответе сканирования: инструмент показывает
`root: prohibit-password` или `root: yes`. Если стоит `prohibit-password`,
пароль сменится, но вход по нему не откроется, пока не поправить конфиг.

## Пароли сервисов и чекер

Чекер проверяет **функциональность**, а не SSH. Смена SSH-пароля ему не мешает.
Ломает его другое:

- смена пароля БД без правки конфига;
- перезапуск сервиса в момент проверки;
- блокировка пользователя, под которым работает процесс;
- `chmod`/`chown` на каталоге, куда сервис пишет.

Поэтому порядок такой: сначала убедиться, что сервис отвечает (`/health`), потом
менять учётку, потом снова проверить `/health` и журнал юнита.

## Локальный полигон

`127.0.0.1:2222` — это sshd внутри WSL-дистрибутива `kali-linux`, проброшенный
на localhost. Если порт пропал, дистрибутив уснул:

```powershell
wsl -d kali-linux -e true
```

и через несколько секунд порт возвращается. Инструмент в этом случае пишет
подсказку про WSL, а не «неверный пароль». Ключ полигона лежит в
`sim/keys/ad_lab`, он же в `authorized_keys` пользователей `root` и `vulnbox`.

## Чек-лист перед игрой

- [ ] `ss -lntp` показывает все сервисы, каждый на своём порту
- [ ] SSH-пароль root сменён (или ключ добавлен), вход проверен вторым окном
- [ ] `sshd -T` показывает ожидаемый `PermitRootLogin`
- [ ] пароли БД не тронуты без конфига
- [ ] чекер проходит: `/srv/_checker/checker.py --once` (в полигоне)
- [ ] в инструменте сохранён хост, порт и учётка; «Проверить связь» показывает
      тот адрес, который ожидали
