# Attack_on_defense — домашний Attack–Defense-тренажёр

Пять небольших намеренно уязвимых HTTP-сервисов для практики команды:

| Сервис | Порт по умолчанию | Язык | Тема | Что отрабатываем |
|---|---:|---|---|---|
| `notes` | 18081 | Python | IDOR / BOLA | поиск объекта checker, чтение чужой приватной записи, исправление проверки владельца |
| `workflow` | 18082 | Python | бизнес-логика | нарушение перехода `unpaid → shipped`, роль владельца, checker и регрессия |
| `search` | 18083 | Python | SQL injection | обнаружение SQL-конкатенации, чтение учебной флаговой записи, параметризованный patch |
| `go-files` | 18084 | Go | path traversal | выход из public-каталога и защита нормализованного пути |
| `rust-profile` | 18085 | Rust | mass assignment | повышение роли через клиентское поле и серверная авторизация |

Каждый сервис — отдельное приложение и отдельная SQLite-база. Checker периодически генерирует **новые случайные** `flag_id` и `TRAINING{...}`, помещает их в сервис и проверяет штатный readback. Перезапуск раунда обновляет флаг. Флаги здесь учебные, не являются флагами финала.

> [!warning] Только изолированная лаборатория
> Все сервисы намеренно уязвимы. По умолчанию Docker публикует порты только на `127.0.0.1`. Не делайте port-forwarding на роутере и не открывайте эти порты в публичный Интернет. Если участники находятся в разных сетях, подключите их через private VPN/overlay (например, Tailscale или WireGuard), ограничьте доступ только адресами команды и не публикуйте checker-интерфейс. Ставьте каждый сервис только на устройства команды и только для этой тренировки.

## Документация тренажёра

- [`DOCKER.md`](DOCKER.md) — развёртывание через Docker Compose, запуск и остановка контейнеров, несколько команд и диагностика.
- [`ПОЯСНЕНИЕ.md`](ПОЯСНЕНИЕ.md) — разбор уязвимостей, демонстрационных атак и способов исправления.


- Docker Desktop с Compose v2 (`docker compose version`) **или** Python 3.11+ для ручного запуска;
- Git не обязателен;
- три участника удобно распределяют роли: 1) защитник/дежурный checker, 2) аналитик, 3) автор exploit. Роли следует менять между раундами.

Все команды ниже выполняются из этой папки `Attack_on_defense`.

## Быстрый старт на одном компьютере (Docker)

1. Скопируйте `.env.example` в `.env`.
2. Поменяйте `CHECKER_TOKEN` на случайную локальную строку. Не коммитьте и не пересылайте `.env`.
3. Запустите:

```sh
docker compose up --build -d
docker compose ps
```

4. Проверьте health endpoints в браузере или терминале:

```text
http://127.0.0.1:18081/health
http://127.0.0.1:18082/health
http://127.0.0.1:18083/health
http://127.0.0.1:18084/health
http://127.0.0.1:18085/health
```

5. Запустите функциональный checker. Подставьте тот же токен, что в `.env`:

```sh
python checker.py --token "local-only-change-me" --team-user blue
```

Ожидается `UP: putflag → readback` для всех пяти сервисов: `notes`, `workflow`, `search`, `go-files`, `rust-profile`. Сохраните вывод и время как журнал раунда.

Остановить все пять сервисов:

```sh
docker compose down
```

Остановить и полностью удалить лабораторные базы/флаги (необратимо):

```sh
docker compose down -v
```

Для обычного завершения используйте только `down`, чтобы базы сохранялись. Перед `down -v` убедитесь, что удаляете именно лабораторию.

## Практика в одном экземпляре: атака и patch

Исходный режим `PATCHED=0` намеренно уязвим. Запустите демонстрацию на своём экземпляре:

```sh
python attack.py notes --base http://127.0.0.1:18081 --id 1
python attack.py workflow --base http://127.0.0.1:18082
python attack.py search --base http://127.0.0.1:18083
python attack.py go-files --base http://127.0.0.1:18084
python attack.py rust-profile --base http://127.0.0.1:18085
```

Для `notes` найдите ID созданной checker-записи в `GET /api/notes` и передайте его через `--id`. Клиент посылает запрос как тестовый `mallory`; в уязвимом режиме handler возвращает чужой объект. Для `workflow` демонстрация пытается отгрузить тренировочный заказ без оплаты. Для `search` используется учебное изменение SQL-запроса. `go-files` показывает выход через `..` из public-каталога, а `rust-profile` — повышение роли через mass assignment. Эти примеры — только для собственных локальных targets.

После демонстрации:

1. Откройте `app.py` и найдите маркеры `INTENTIONAL IDOR`, `INTENTIONAL WORKFLOW BUG`, `INTENTIONAL SQL INJECTION`.
2. Патчьте правило на серверной стороне:
   - `notes`: всегда связывать ID записи с текущим пользователем (`WHERE id=? AND owner=?`); checker должен создавать запись в проверяемой команде.
   - `workflow`: атомарно проверять владельца и оплату до отгрузки; не возвращать delivery code до законного перехода состояния.
   - `search`: передавать значение в SQL отдельно: `WHERE title LIKE ?` с tuple параметров; имена колонок/сортировки — только allowlist.
   - `go-files`: нормализовать путь и подтверждать, что он остаётся внутри `public`; лучше использовать allowlist файлов.
   - `rust-profile`: не принимать `role` из публичного JSON; разделять DTO обновления профиля и серверную модель полномочий.
3. Для Docker перезапустите с patch-режимом:

```sh
PATCHED=1 docker compose up --build -d
python checker.py --token "local-only-change-me" --team-user blue
```

В PowerShell перед командами задайте `$env:PATCHED='1'`. Чтобы вернуть уязвимый режим: `$env:PATCHED='0'`, затем снова `docker compose up --build -d`.

4. Повторите тесты: exploit больше не раскрывает приватные данные/не обходит шаг, а штатный checker проходит. `PATCHED=1` дополнительно включает защитные проверки в коде — это режим проверки поведения, а не автоматическая оценка качества вашего ручного patch.

> В этом учебном стенде флаг доступен для checker в data path соответствующего сервиса. Не меняйте checker-токен на стороне атакующего; атакующие запросы идут по публичным API. Checker endpoints `/_checker/*` служебные, их не следует публиковать.

## Три участника, три отдельные команды/экземпляра

Compose project name создаёт отдельные контейнеры и volumes. Так имитируются одинаковый код и разное состояние/флаги команд. На одном компьютере можно запустить три экземпляра с разными host-портами.

Пример для одного компьютера (каждый project — отдельный «target»):

```sh
TEAM_ID=blue NOTES_PORT=18081 WORKFLOW_PORT=18082 SEARCH_PORT=18083 GO_FILES_PORT=18084 RUST_PROFILE_PORT=18085 docker compose -p team-blue up --build -d
TEAM_ID=red  NOTES_PORT=18181 WORKFLOW_PORT=18182 SEARCH_PORT=18183 GO_FILES_PORT=18184 RUST_PROFILE_PORT=18185 docker compose -p team-red up --build -d
TEAM_ID=green NOTES_PORT=18281 WORKFLOW_PORT=18282 SEARCH_PORT=18283 GO_FILES_PORT=18284 RUST_PROFILE_PORT=18285 docker compose -p team-green up --build -d
```

Для каждого экземпляра задайте свой `CHECKER_TOKEN`; не используйте один production-секрет. На Windows PowerShell значения передавайте через env перед запуском, например:

```powershell
$env:TEAM_ID='blue'; $env:NOTES_PORT='18081'; $env:WORKFLOW_PORT='18082'; $env:SEARCH_PORT='18083'; $env:GO_FILES_PORT='18084'; $env:RUST_PROFILE_PORT='18085'; $env:CHECKER_TOKEN='blue-local-token'; docker compose -p team-blue up --build -d
```

Замените `blue` на `red`/`green`, порты и токен — на соответствующие. Не запускайте два проекта на одинаковых портах. Проверить каждый экземпляр:

```text
http://127.0.0.1:18081/health  # blue notes
http://127.0.0.1:18181/health  # red notes
http://127.0.0.1:18281/health  # green notes
```

Checker проверяет экземпляр как доступный и выполняет putflag/readback. Для каждого project запустите checker отдельно с его токеном и URL. `attack.py` принимает URL одного выбранного сервиса; атакующий должен записать target, сервис, полученные `flag_id`, приём/отказ checker и время раунда. Не считайте `HTTP 200` доказательством очков — здесь результат атаки следует сопоставить с текущей записью и результатом checker.

Остановить конкретную команду без удаления её данных:

```sh
docker compose -p team-red down
```

Полностью сбросить только конкретный проект вместе с его базами:

```sh
docker compose -p team-red down -v
```

## Доступ команды из разных сетей (белый IP не требуется)

**Рекомендуемый способ — private VPN/overlay.** Установите Tailscale/WireGuard на компьютеры участников, создайте отдельную командную сеть и разрешите вход к нужным портам только участникам. Белый IP на хосте-сервере обычно не нужен: overlay связывает устройства через NAT traversal или relay.

Docker Compose по умолчанию слушает только loopback. Для доступа по VPN:

1. Убедитесь, что VPN каждого участника работает и адреса видны между собой.
2. В `docker-compose.yml` поменяйте публикации `127.0.0.1:...` на bind-адрес VPN-хоста, например `100.x.y.z:18081:8081` (укажите именно адрес хоста в приватной VPN-сети; синтаксис `host-ip:host-port:container-port`). Не используйте `0.0.0.0`, если это не нужно.
3. В firewall разрешите порты 18081–18085 только для VPN-интерфейса/подсети и участников команды; убедитесь с другого устройства, что они доступны по VPN, но не по обычному публичному адресу.
4. В `checker.py`/`attack.py` указывайте приватный VPN IP машины с сервисом, например `http://100.x.y.z:18081`.
5. Никогда не публикуйте `/_checker/*` или этот учебный стенд на публичный IP без VPN, allowlist/firewall и отдельного осознанного согласования команды. Не делайте проброс портов на домашнем роутере. Не отключайте firewall «для удобства».

Если VPN-хост должен быть публично доступен, это уже изменение модели угроз: безопаснее использовать настроенный WireGuard/Tailscale, а не выставлять уязвимое приложение наружу. Публичный reverse proxy/tunnel сам по себе не делает намеренно уязвимый сервис безопасным.

## Запуск без Docker (Python)

В трёх отдельных терминалах из этой папки, с Python 3.11+:

**PowerShell (Windows):**

```powershell
$env:SERVICE='notes'; $env:TEAM_ID='blue'; $env:PATCHED='0'; $env:PORT='18081'; $env:HOST='127.0.0.1'; $env:DB_PATH='.\data\blue-notes.sqlite3'; python app.py
```

```powershell
$env:SERVICE='workflow'; $env:TEAM_ID='blue'; $env:PATCHED='0'; $env:PORT='18082'; $env:DB_PATH='.\data\blue-workflow.sqlite3'; python app.py
```

```powershell
$env:SERVICE='search'; $env:TEAM_ID='blue'; $env:PATCHED='0'; $env:PORT='18083'; $env:DB_PATH='.\data\blue-search.sqlite3'; python app.py
```

Порты вручную в этом режиме по умолчанию слушаются на `127.0.0.1`; для доступа из private VPN явно задайте `HOST` равным VPN-адресу машины и добавьте firewall allowlist. Для другой машины/команды меняйте `TEAM_ID`, `PORT`, `DB_PATH` и `CHECKER_TOKEN`; используйте разные DB пути.

Зависимости внешних Python-пакетов отсутствуют: используются стандартная библиотека Python и SQLite. Утилиты `attack.py` и `checker.py` также работают на стандартной библиотеке.

## API и флаговый цикл для команды

Общие endpoints:

- `GET /health` — доступность, имя сервиса и режим `patched`.
- `GET /api/notes` — список ID/title тренировочных заметок (notes).
- `GET /api/notes/{id}` — чтение заметки с заголовком `X-User` (notes).
- `GET /api/orders` и `GET /api/orders/{id}` — список заказов/статус (workflow).
- `POST /api/orders/{id}/ship` — действие отгрузки (workflow).
- `GET /api/search?q=...` — поиск по базе знаний (search).
- `POST /_checker/putflag` — checker ставит свежие `flag_id`/`flag`.

Checker защищён заголовком `X-Checker-Token`. Он генерирует свежий флаг для каждого запуска. В реальном матче формат обновления флагов/сдачи задаётся платформой; этот локальный protocol лишь упражнение, не копия неизвестных деталей финала.

## Предлагаемый раунд на 45–60 минут

1. **0–5 мин:** защитник поднимает все сервисы; команда проверяет `/health`, запускает checker и сохраняет baseline.
2. **5–15 мин:** аналитик читает `app.py` и checker, формулирует инварианты и отмечает подозрительные места, не запускает массовые сканы.
3. **15–25 мин:** атакующий запускает по одному демонстрационному клиенту против конкретного локального экземпляра; записывает endpoint, ответ и flag_id.
4. **25–35 мин:** защитник вносит один patch и перезапускает только нужный сервис в `PATCHED=1`/ручном исправленном режиме.
5. **35–45 мин:** команда повторяет exploit и checker; проверяет, что штатные операции живы.
6. **45–60 мин:** роли меняются; новый владелец объясняет баг/patch без подсказок.

Журнал:

```text
Раунд / дата:
Команда-target / URL / сервис:
Штатная проверка checker:
Инвариант и гипотеза:
Уязвимая функция:
Запрос/PoC и наблюдение:
Flag ID и результат checker:
Patch:
Эксплойт после patch:
Checker после patch:
Откат/следующий шаг:
```

## Устранение неполадок

- **Порт занят:** выберите другой `NOTES_PORT`/`WORKFLOW_PORT`/`SEARCH_PORT`; для другого Compose-проекта обязательно другие host-порты.
- **Docker не запускается:** проверьте `docker info`, `docker compose version`, права и свободное место.
- **Checker получает 403:** его `--token` должен совпадать с `CHECKER_TOKEN` конкретного экземпляра.
- **База/флаг не сбрасывается:** это ожидаемо после `docker compose down`; удаляйте volume только командой `down -v` для нужного project.
- **Изменили `PATCHED`, но код не перезапустился:** Compose пересоздаёт контейнер, когда env/compose конфигурация изменилась; проверьте `docker compose config` и `docker compose ps`.
- **Друг участник не видит сервис:** сначала проверьте private VPN reachability и firewall; не решайте это пробросом порта наружу.

## Файлы

- `app.py` — три Python-сервиса и две реализации поведения: уязвимая и защитная.
- `go-files/` — отдельный Go-сервис с собственным Dockerfile.
- `rust-profile/` — отдельный Rust-сервис с Cargo-проектом и Dockerfile.
- `checker.py` — создание свежих флагов и функциональная проверка всех пяти сервисов.
- `attack.py` — минимальные учебные клиенты для пяти классов уязвимостей.
- `test_lab.py`, `test_native_services.py` — локальные интеграционные и native smoke-тесты.
- `docker-compose.yml`, Dockerfiles, `.env.example` — локальное развёртывание.
- `requirements.txt` — внешние Python-зависимости не требуются.
