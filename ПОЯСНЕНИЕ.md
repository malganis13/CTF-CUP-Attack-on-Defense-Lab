# Пояснение: уязвимости, атаки и исправления

Этот документ разбирает пять специально заложенных уязвимостей в `app.py`, `go-files/main.go` и `rust-profile/src/main.rs`. Проводите проверки только на собственной лаборатории. Все примеры ниже рассчитаны на локальные адреса `127.0.0.1` и данные тренажёра.

## 1. `notes`: IDOR / BOLA — доступ к чужому объекту

### Где ошибка

В `Handler.do_GET`, обработчик `GET /api/notes/{id}`. В уязвимом режиме запрос ищет запись только по идентификатору:

```python
row = db.execute(
    "SELECT id,owner,title,body FROM notes WHERE id=?",
    (note_id,),
).fetchone()
```

Идентификатор объекта — не доказательство права на него. Злоумышленник может перечислить ID и прочитать заметку другого пользователя. Это IDOR (Insecure Direct Object Reference), также называемая BOLA в API-контексте.

### Как воспроизвести

1. Запустите лабораторию в уязвимом режиме.
2. Получите список объектов: `GET http://127.0.0.1:18081/api/notes`.
3. Запросите ID тестового пользователя с другой идентичностью:

```sh
python attack.py notes --base http://127.0.0.1:18081 --id 1
```

Клиент отправляет `X-User: mallory`. В уязвимом режиме ответ содержит запись alice, потому что владелец не проверяется.

Для checker-флага его ID можно найти в `GET /api/notes`; затем проверить доступ как `mallory`. Сам флаг случайный и меняется при очередной установке checker’ом.

### Исправление

Проверяйте полномочия на сервере для каждого объекта. Идентичность должна происходить из настоящей аутентифицированной сессии, а не из произвольного заголовка, который пользователь может подделать:

```python
row = db.execute(
    "SELECT id,owner,title,body FROM notes WHERE id=? AND owner=?",
    (note_id, authenticated_user.id),
).fetchone()
```

В реальном приложении также проверяют права на изменение/удаление, не раскрывают лишние поля и добавляют тест, что чужой объект недоступен. Здесь `X-User` — упрощённая учебная имитация, не настоящая аутентификация.

### Не сломать checker

Checker-флаг принадлежит `TEAM_ID` (по умолчанию `blue`). Проверяйте чтение флага с авторизацией именно этой команды. Не убирайте проверку владельца глобально и не делайте все заметки общедоступными.

## 2. `workflow`: нарушение бизнес-инварианта

### Где ошибка

В `Handler.do_POST`, `POST /api/orders/{id}/ship`. Уязвимая версия разрешает отгрузку заказа пользователя без проверки оплаты. Обычный happy path может работать, но нарушается инвариант: неоплаченный заказ не должен перейти в `shipped` и открыть delivery code.

### Как воспроизвести

```sh
python attack.py workflow --base http://127.0.0.1:18082
```

Клиент выбирает тренировочный заказ alice и вызывает отгрузку до оплаты. В уязвимой версии возвращаются успешный статус и delivery code. В режиме `PATCHED=1` тот же шаг должен быть отклонён ответом `409 payment required`.

Проверяйте не только ответ HTTP, но и изменившееся состояние заказа и доступность секретного поля. Иногда endpoint отвечает ошибкой после частичного изменения состояния — это тоже ошибка.

### Исправление

На сервере атомарно проверьте право пользователя и требуемое состояние, затем выполните переход. Не полагайтесь на скрытую кнопку в UI или на то, что клиент «сначала оплатит»:

```python
if order["owner"] != authenticated_user.id:
    return forbidden()
if not order["paid"]:
    return conflict("payment required")
# Только после проверок выполнить переход в транзакции.
```

Для конкурентных запросов проверку и обновление делают транзакционно/условным `UPDATE`, например обновляют только `WHERE paid=1 AND shipped=0 AND owner=?`, а затем проверяют количество изменённых строк. Delivery code возвращают только после допустимого перехода.

### Не сломать checker

Checker в этом стенде сначала создаёт checker-заказ, затем через закрытый служебный маршрут ставит его в состояние paid и проходит обычный путь отгрузки. Это демонстрирует разницу между проверкой публичного процесса и служебной установкой состояния. В настоящем соревновании checker-протокол может быть другим: не угадывайте его, читайте выданный код и сохраняйте ожидаемые им переходы.

## 3. `search`: SQL injection

### Где ошибка

В обработчике `GET /api/search?q=...`. Уязвимая версия вставляет пользовательское значение прямо в SQL:

```python
sql = f"SELECT title,body FROM articles WHERE title LIKE '%{q}%'"
rows = db.execute(sql).fetchall()
```

Ввод становится частью синтаксиса SQL, поэтому может менять условие запроса и читать таблицу `flags`.

### Как воспроизвести

```sh
python attack.py search --base http://127.0.0.1:18083
```

Пример-клиент посылает SQLite payload, который объединяет результат поиска с таблицей `flags`. В уязвимом режиме ответ содержит текущую учебную запись `TRAINING{...}`. Не передавайте этот payload никакому адресу, кроме собственного стенда.

### Исправление

Параметризуйте значения — SQL-код и пользовательские данные должны идти раздельно:

```python
rows = db.execute(
    "SELECT title,body FROM articles WHERE title LIKE ?",
    (f"%{q}%",),
).fetchall()
```

Параметры защищают **значения**, но не заменяют валидацию динамических имён колонок, таблиц или направления сортировки. Для таких частей используйте фиксированный allowlist. Ограничьте длину ввода, права DB-аккаунта и доступ приложения к секретам.

### Не сломать checker

Checker должен уметь установить флаг через служебный интерфейс и проверить его целостность. Исправление публичного поиска не требует выдавать публичному API таблицу `flags`. Проверьте, что полезный обычный поиск продолжает возвращать статьи, а инъекционный ввод трактуется как обычная строка.

## 4. `go-files`: path traversal

### Где ошибка

В `go-files/main.go`, обработчик `GET /api/files/download?name=...`. В уязвимом режиме имя объединяется с `public/` без проверки, что итоговый путь остался внутри разрешённой директории:

```go
target = filepath.Join(publicRoot(), filepath.FromSlash(name))
```

Это позволяет использовать `..` и читать файл за пределами `public/`. В стенде checker хранит учебный флаг в `private/blue/flag.txt`.

### Как воспроизвести

```sh
python attack.py go-files --base http://127.0.0.1:18084
```

Клиент запрашивает `../private/blue/flag.txt`. В уязвимом режиме ответ раскрывает содержимое файла. В `PATCHED=1` запрос должен получить `403`.

### Исправление

Разрешайте только нормализованный путь, который остаётся под корнем public-каталога, и лучше используйте allowlist имён файлов:

```go
candidate := filepath.Join(publicRoot(), filepath.FromSlash(name))
relative, err := filepath.Rel(publicRoot(), candidate)
if err != nil || relative == ".." || strings.HasPrefix(relative, ".."+string(os.PathSeparator)) {
    return forbidden()
}
```

Нельзя полагаться только на удаление `../`: учитывайте кодирование, разделители платформы, symlink’и и целевой endpoint. Для production стоит запретить symlink escape и отдавать только заранее известные файлы.

## 5. `rust-profile`: mass assignment / повышение роли

### Где ошибка

В `rust-profile/src/main.rs`, обработчик `PUT /api/profile`. Уязвимая ветка принимает поле `role` от клиента и сохраняет его:

```rust
let role = if is_patched { "member" } else { requested_role };
```

Клиент может назначить себе `admin`, после чего `/api/admin/secret` отдаёт checker-флаг. Это пример mass assignment и нарушения серверной модели авторизации.

### Как воспроизвести

```sh
python attack.py rust-profile --base http://127.0.0.1:18085
```

Клиент отправляет `PUT /api/profile {"role":"admin"}`, затем читает `/api/admin/secret`. В уязвимом режиме второй запрос возвращает учебный флаг; в исправленном режиме роль остаётся `member`, а endpoint отвечает `403`.

### Исправление

Используйте отдельную структуру входных данных, в которой нет серверных полей `role`, `id`, `owner` и т.п. Роль изменяется только отдельным административным workflow после проверки полномочий:

```rust
// PublicUpdate содержит только разрешённые пользовательские поля.
// role берётся из серверной сессии/БД и не десериализуется из тела запроса.
let role = "member";
```

Проверяйте авторизацию на каждом admin endpoint, а не только при отображении кнопки. Не храните доверенные роли в клиентском JSON.

## Режим `PATCHED`

Переменная `PATCHED=1` включает в учебных приложениях защитные ветви кода для пяти демонстраций. Это эталон поведения, а не магический патчер ваших изменений. Для обучения рекомендуемый цикл такой:

1. На отдельной лабораторной копии изучите endpoint и зафиксируйте baseline checker.
2. Сформулируйте инвариант и воспроизведите ошибку по одному разу.
3. Измените серверный handler сами, затем повторите тот же тест.
4. Запустите checker и функциональные проверки; убедитесь, что штатный сценарий работает.
5. Сравните своё исправление с ветвью `PATCHED=1` и объясните, какие проверки нужны в production.

Тесты обоих режимов:

```sh
python test_lab.py
```

Ожидаются шесть `PASS` от Python-интеграционных тестов и native smoke-тесты Go/Rust, если соответствующие toolchain установлены. В CI toolchain устанавливаются автоматически.

## Границы модели

- `X-User` не является безопасной аутентификацией; он нужен только для понятной демонстрации контроля владельца.
- Checker token — упрощённый секрет лаборатории. Не храните его в публичном репозитории и не публикуйте checker endpoints.
- Учебный флаг — случайная метка, не флаг настоящего CTF.
- Стенд не реализует очки, таймер раунда, сетевой арбитр или точную инфраструктуру конкретного финала.
- Уязвимый режим предназначен только для изолированных targets команды. В Docker порты по умолчанию связаны с loopback.
